# CEO Brief: FDE 商業模型與 NIMBL 的未來

日期：2026-06-04  
目的：從 CEO 角度說明為什麼公司應該把既有的現場改善、AI 工具導入、產品回饋與客戶 workflow 協作，制度化成 FDE operating model；並回答 NIMBL 未來應如何演化。

## 1. 一句話結論

我們不是從零開始建立 FDE。公司內部已經有種子 FDE 行為：有人進到真實流程改善效率，有人分析現場作業，有人使用 AI 生態軟體後回饋產品 gap，也有人根據使用者意見把工具做出來。

現在缺少的不是能力，而是制度化：

> 把分散發生的現場 workflow 改善、know-how 萃取、產品 gap 回饋與 AI 工具建置，整理成一套可重複、可驗收、可收費、可回饋產品的 FDE operating model。

商業模型應分成兩層：

1. FDE engagement revenue：客戶付費讓我們進入 workflow，做 diagnostic、prototype、pilot、deployment。這不是賣人天，而是賣 workflow outcome、AI 導入落地與風險降低。
2. Productized AI ecosystem revenue：FDE 把現場驗證過的 workflow pattern、connector、agent skill、eval、runbook、control loop 沉澱進公司產品生態，形成可重複銷售的產品收入。

NIMBL 是這個模型的重要落地場域，但不是唯一產品。FDE 應該服務整個公司 AI product ecosystem，包括 NIMBL、aaagent / KM system、內部 AI tooling、產業 workflow module、connector package、agent skill library、eval / audit / monitoring tooling。

## 2. 我們已經有種子 FDE

目前公司內部已經出現類似 FDE 的工作模式，只是尚未被命名、制度化與商業化。

| 既有案例 | 實際發生的行為 | FDE 意義 |
| --- | --- | --- |
| 香閔協助採購減輕生產流程中某一環節的複雜度和效率問題 | 進入既有 workflow，理解痛點，改善流程負擔 | Workflow optimization |
| 靜慧進入 Atop 生管分析流程，嘗試協助改善 | 進到現場作業脈絡，觀察資料、流程、決策與 handoff | Workflow discovery / process analysis |
| 桂弘使用公司的 AI 生態軟體並提供具體建議 | 真實使用者回饋產品與 workflow 之間的 gap | Product gap discovery |
| Alan 和我根據前端人員意見開發合適的軟體 | 把現場需求轉成可用工具，再回饋產品能力 | Build-prove-generalize |

這些不是零散事件，而是同一種能力的不同面向：

- 看懂真實工作流。
- 找出可以改善的窄場景。
- 把人的 know-how 轉成工具、流程、skill 或 runbook。
- 讓產品更貼近使用者真正的工作方式。
- 從現場 case 中萃取可重複模式。

所以 FDE 對公司而言不是新創一個外來概念，而是把已經在發生的高價值行為整理成一套正式機制。

## 3. 為什麼要制度化

如果不制度化，這些行為會繼續依賴個人熱情與偶發機會：

- 有人做了流程改善，但沒有變成可複製 playbook。
- 有人理解了現場 know-how，但沒有沉澱成 AI asset。
- 有人聽到產品建議，但沒有形成 product gap report 與 owner。
- 有人做出工具，但沒有 eval、runbook、trace、handoff。
- 有人成功幫了一個部門或客戶，但下一個案子又重新摸索。

制度化 FDE 的目的，是把這些行為變成公司能力：

- 每個案子都有 qualification，避免接錯題。
- 每個案子都有 workflow map、baseline、success metric。
- 每個 prototype 都有 trace、eval、human approval、failure taxonomy。
- 每個 pilot 都有 adoption、error、cycle time、operator feedback。
- 每個 production 都有 runbook、monitoring、rollback、handoff。
- 每個 engagement 都產出 skill asset 與 product gap report。
- 每個可重複 pattern 都回到產品、平台或銷售/CS enablement。

## 4. 商業模型：雙層收入

### 4.1 第一層：FDE engagement revenue

第一層收入來自客戶付費導入：

- Diagnostic：進入客戶 workflow，找出可導入 AI 的 1-3 個高價值場景。
- Prototype / Tracer Bullet：做出一個可操作的端到端 agent workflow，驗證技術與使用價值。
- Controlled Pilot：讓小範圍真實使用者在受控環境中使用。
- Production Deployment：完成安全、權限、audit、rollback、monitoring、runbook、handoff。
- Post-Launch Retainer：維持、改善、incident、版本更新與追加 workflow discovery。

這層不能賣成一般顧問人天，因為人天會讓客戶覺得買的是人，不是成果，也會讓公司承擔 scope creep。

比較好的定位是：

> 我們賣的是 workflow outcome、AI adoption risk reduction、production readiness 與可重複 AI asset 的建立。

階段式固定價會比純 hourly 更健康：

- 每階段有明確 deliverables。
- 每階段有 acceptance criteria。
- 客戶依賴項明確列出。
- 超出範圍走 change request。
- 模型費、雲端、第三方 SaaS、差旅、資安稽核另計。
- 生產後支援另走 retainer。

### 4.2 第二層：Productized AI ecosystem revenue

第二層收入來自產品化。

FDE 不是最終目的，而是一個現場驗證與產品化引擎。每個 engagement 都應該問：

- 這個 workflow pattern 是否會在其他客戶重複出現？
- 這個 connector 是否應該產品化？
- 這個 agent skill 是否可以變成公司 AI asset？
- 這個 eval / audit / monitoring pattern 是否可重用？
- 這個 product gap 是單一客戶特例，還是產品應該補上的能力？

可產品化的收入來源包括：

- NIMBL network operations modules。
- aaagent / KM system。
- agent skill library 或 marketplace。
- workflow automation modules。
- connector packages。
- eval / audit / monitoring tooling。
- vertical solution packages，例如生管、採購、客服、維運、文件審查。
- 產業專屬 runbook、dashboard、approval loop、control loop。

因此第二層不是綁定單一產品，而是公司整體 Productized AI ecosystem 的收入。

### 4.3 兩層收入如何互相增強

FDE engagement revenue 解決短期現金流與客戶落地問題；Productized AI ecosystem revenue 解決長期 scale 與毛利問題。

健康循環應該是：

1. FDE 進入真實 workflow。
2. 做出可驗證 prototype / pilot。
3. 產生 workflow outcome。
4. 萃取 skill、eval、runbook、connector、control loop。
5. 分類 product gap。
6. 將可重複 pattern 產品化。
7. 下一個 engagement 更快、更便宜、更有把握。
8. 產品收入與導入收入互相推動。

如果只做第一層，公司會變成 AI 顧問或外包。  
如果只想做第二層，產品團隊容易靠內部想像做 roadmap，離客戶現場太遠。

FDE 的價值就是把兩層接起來。

## 5. NIMBL 的未來是什麼

Eric 問「NIMBL 的未來是什麼」，建議回答不要只是功能 roadmap，也不要只說「加 AI」。

更好的答案是：

> NIMBL 的未來，是從傳統 network management system，演化成由真實案場 workflow 驅動的 AI-assisted network operations platform。

NIMBL 不應該只是一組制式功能：

- alarm management。
- topology。
- dashboard。
- report。
- device monitoring。
- ticket integration。

這些仍然重要，但不足以回答客戶真正的日常問題。使用 NIMBL 的客戶通常都有複雜案場，而複雜案場的價值不只在「看見資料」，而在「如何判斷、處理、升級、交接、復盤」。

因此 NIMBL 的未來 roadmap 應該從 feature-driven 轉向 case-driven / workflow-driven。

NIMBL AI 應該關心的是：

- 某種異常如何被發現。
- operator 如何判斷嚴重性。
- 要查哪些設備、告警、log、拓撲、歷史事件。
- 哪些狀況可以建議處理方式。
- 哪些 action 必須人工批准。
- 哪些情境必須升級。
- 哪些判斷可以沉澱成 NIMBL AI skill。
- 哪些案場 pattern 可以變成可重複 module。

## 6. NIMBL 不應捨棄 roadmap，而是改變 roadmap 來源

「捨棄制式化 roadmap」的意思不是不要 roadmap，而是不要閉門造車式 roadmap。

NIMBL 仍然需要 roadmap，但 roadmap 的來源應該從內部功能想像，轉成 FDE case evidence。

每個 NIMBL FDE case 都要回答：

- 這是單一客戶客製化，還是可重複 network operations pattern？
- 這個需求應該變成產品功能、connector、agent skill、dashboard、runbook，還是導入 playbook？
- 這個 gap 是 NIMBL 核心產品問題、platform tooling 問題、文件/onboarding 問題，還是客戶資料與權限 readiness 問題？
- 這個 pattern 對下一個案場有沒有幫助？

所以 NIMBL 的 roadmap 機制應該變成：

> FDE case -> workflow evidence -> reusable pattern -> roadmap decision -> productized module。

這讓 NIMBL 的 AI 整合不是一個單次功能專案，而是一個持續從案場學習、驗證、產品化的系統。

## 7. NIMBL + FDE 的商業包裝

NIMBL 可以作為 FDE 商業模型的第一個強場景，因為 network operations 天然具備：

- 複雜案場。
- 多系統資料。
- 告警判斷。
- operator know-how。
- 升級流程。
- incident 復盤。
- 權限與審批。
- 高度依賴經驗的 troubleshooting。

建議包成三種 offer：

### 7.1 NIMBL Workflow Diagnostic

目的：進入客戶案場，盤點 network operation workflow，找出 1-3 個可導入 AI-assisted improvement 的高價值場景。

交付：

- workflow map。
- pain point / baseline。
- candidate AI workflows。
- system boundary。
- data / permission readiness。
- first pilot recommendation。

### 7.2 NIMBL AI Workflow Pilot

目的：選一個高價值 workflow，接 NIMBL 資料、operator feedback、approval loop、trace / eval，做受控 pilot。

交付：

- pilot-ready agent workflow。
- eval report。
- trace / logging。
- human approval flow。
- adoption metrics。
- failure taxonomy。
- validated NIMBL AI skill draft。

### 7.3 NIMBL AI Operations Platform

目的：把 pilot 成功的 workflow 沉澱成 NIMBL 產品模組、AI skill、dashboard、connector、runbook 與 monitoring / control loop。

交付：

- productized workflow module。
- reusable connector 或 data integration pattern。
- NIMBL AI skill。
- production runbook。
- monitoring / control loop。
- post-launch retainer / platform subscription。

## 8. 但 FDE 不只服務 NIMBL

NIMBL 是重要場景，但 FDE 機制應該服務整個公司產品生態。

同一套模式也可以應用在：

- 生管：分析排程、交期、異常、缺料與跨部門 handoff。
- 採購：供應商、報價、交期、規格確認、例外處理。
- KM / aaagent：把知識、文件、SOP、經驗轉成可執行 skill。
- 客服：ticket triage、回覆建議、升級判斷。
- 維運：incident handling、root cause analysis、runbook execution。
- 內部開發流程：AI coding workflow、review、測試、文件、release。

因此對 CEO 的重點是：

> NIMBL 是 FDE 驅動產品化的第一個核心場景，但 FDE 不應被定義成 NIMBL 導入團隊。FDE 是公司把真實 workflow 轉成 AI 產品能力的橫向機制。

## 9. CEO 應該關心的管理問題

要讓這個模型成立，CEO 需要關心的不是「有沒有成立一個新部門」而已，而是以下管理機制：

### 9.1 每個 engagement 是否產生三類 outcome

- Workflow outcome：效率、品質、可觀測性或 baseline。
- AI asset outcome：skill、eval、runbook、template、failure taxonomy。
- Product learning outcome：product gap、platform gap、導入 playbook gap。

### 9.2 FDE 是否避免變成客製化外包

每個 case 都要有 reusable pattern review。若不可重用，要明確說明原因。

### 9.3 R&D 是否真的接收到現場 evidence

不能只把報告丟給產品團隊。需要 owner、review meeting、roadmap decision、platform backlog。

### 9.4 Training 是否建立在真實案例上

不要一開始做認證課程。先跑 1-2 個真實 engagement，累積 war story、failure taxonomy、good / bad scope example，再做 apprenticeship 和 scenario drill。

### 9.5 收入是否同時推動服務與產品

FDE engagement 要能收費，但更重要的是產出可產品化資產。否則只會變成顧問收入，難以 scale。

## 10. 建議的 90 天行動

### 10.1 盤點種子 FDE case

把目前已發生的案例整理成 4 份 short case brief：

- 香閔 / 採購流程改善。
- 靜慧 / Atop 生管分析。
- 桂弘 / AI 生態軟體使用回饋。
- Alan + 我 / 根據前端意見開發合適工具。

每份 brief 回答：

- workflow 是什麼？
- 痛點是什麼？
- 做了什麼改善？
- 有哪些 know-how 可以 skill 化？
- 有哪些 product gap？
- 哪些 pattern 可重複？

### 10.2 選一個 NIMBL FDE pilot

等 NIMBL AI 整合功能達到可操作狀態後，選一個客戶或內部模擬案場做 FDE pilot。

不要選最宏大的案場，要選一個窄 workflow，例如：

- 告警 triage。
- 週期性維運報告。
- incident 初步判斷。
- operator handoff。
- 特定設備異常 troubleshooting。

### 10.3 建立 FDE operating rhythm

每個 engagement 固定產出：

- workflow map。
- baseline / success metrics。
- agent spec。
- eval report。
- skill asset。
- product gap report。
- build / prove / generalize retrospective。

### 10.4 建立 roadmap intake 機制

建立一個 FDE -> product / platform 的 intake review：

- 每兩週或每月一次。
- 由 FDE、NIMBL R&D、platform、CS / sales enablement 參與。
- 每個 gap 都要標記 owner、狀態、下一步。
- 只有經過 case evidence 支撐的 pattern 才進 roadmap。

## 11. 對 Eric 的建議回答

如果 Eric 問「NIMBL 的未來是什麼」，可以這樣回答：

> NIMBL 的未來不是只做更多制式功能，也不是單純把 AI 加進既有頁面。NIMBL 應該成為 AI-assisted network operations platform。使用 NIMBL 的客戶都有複雜案場，而複雜案場真正需要的是把告警、拓撲、設備資料、operator know-how、升級流程與處理紀錄串成可執行 workflow。  
>
> 我們會用 FDE 的方式進入真實案場，從每個 case 找出有價值、可重複的 network operations workflow。成功的 pattern 會被沉澱成 NIMBL 的 AI skill、connector、dashboard、runbook、approval loop、monitoring / control loop，進入產品 roadmap。  
>
> 所以 NIMBL 不會放棄 roadmap，而是放棄閉門造車式 roadmap。未來 roadmap 會由 FDE case evidence 驅動：從真實案場驗證，再產品化成可重複銷售的能力。這個方法也不只適用 NIMBL，而是公司整體 AI product ecosystem 的成長方式。

## 12. 核心風險

### 12.1 只做服務，不產品化

如果 FDE 只收導入費，不沉澱產品能力，公司會變成 AI 顧問或客製化外包。

### 12.2 只做產品，不進現場

如果產品 roadmap 仍靠內部想像，AI 功能容易變成 demo，而不是客戶日常 workflow。

### 12.3 Pattern 被隔牆交接

不能成立一個不在現場的 analyst team 事後看報告萃取 pattern。真正的 pattern 判斷要由原 squad 負責，platform / R&D 協助 productionize。

### 12.4 NIMBL 被過度特殊化

NIMBL 是重要場景，但 FDE 不應只服務 NIMBL。否則公司會錯過其他 workflow 與產品生態的產品化機會。

### 12.5 收費被拉回人天

如果商業包裝變成 hourly consulting，客戶會買人天，公司會承擔 scope creep。應改用階段固定價、deliverables、acceptance criteria 與 change request。

## 13. 最終定位

FDE 對公司不是一個新的顧問部門，而是一個商業與產品成長機制：

- 對客戶：降低 AI 導入風險，改善真實 workflow。
- 對產品：用真實 case evidence 驅動 roadmap。
- 對公司：把 know-how 變成 AI asset，把服務收入轉成產品收入。
- 對 NIMBL：從 network management system 演化成 AI-assisted network operations platform。
- 對整體產品生態：讓每個成功 workflow 都有機會變成可重複銷售的產品能力。
